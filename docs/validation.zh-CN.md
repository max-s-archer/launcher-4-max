# 验证指南

> 英文语义源：[validation.md](validation.md)。本文件是其中文对应版本。

## 目的

本文定义 Launcher4Max 当前最小验证基线：存在哪些检查、谁可以发起检查、如何记录设备观察，以及如何报告结果。它将“存在可用命令”与“命令已经实际通过的证据”明确分开。

## 执行权限

- 项目作者通常执行构建、安装和真机使用检查，并可将观察结果报告为迭代或版本证据。
- 只有项目作者明确要求，或已授权正式版本或聚焦验证任务需要时，Agent 才运行 Gradle。
- 实现迭代的授权包含与风险相称的本地验证，但不覆盖上一条 Gradle 限制。
- 下列命令是权威执行入口。在当前证据记录实际执行前，其结果仍为 `Not run` 或 `Unknown`。

## 可用自动化检查

在仓库根目录执行命令；POSIX shell 使用 `./gradlew`，Windows 使用 `gradlew.bat`。

| 检查 | Gradle task | 当前范围 |
| --- | --- | --- |
| 组装 debug APK | `assembleDebug` | 编译并打包 debug 应用 |
| JVM 单元测试 | `testDebugUnitTest` | 存在 `app/src/test` 测试时运行这些测试 |
| Android lint | `lintDebug` | 对 debug variant 运行当前配置的 Android lint |
| 已连接 Android 测试 | `connectedDebugAndroidTest` | 在已连接兼容目标上运行 `app/src/androidTest` 测试 |

当前工程包含 Android instrumentation 测试，不存在仓库 JVM 单元测试源码目录。某项任务成功但没有适用测试时，必须如实报告，不得描述为实际不存在的行为覆盖。除已配置的 Android lint 外，当前尚未建立独立静态分析工具。

上述 task 名称来自已检入的 Android 应用配置，建立本文时并未执行这些命令。如果 Gradle 表明某个已记录 task 不存在或不适用，应保留该结果，依据仓库证据修正文档，不得静默改用范围更广的 task。

## 聚焦人工验证

产品行为发生变化时，依据适用产品或迭代验收条件选择最小且有意义的人工路径。记录：

- APK 或构建标识及源码 commit；
- 设备型号、Android 版本和 API 级别；
- 准确起始状态与执行步骤；
- 观察结果，包括失败或不确定情况；
- 检查前后的相关应用状态；以及
- 观察由作者还是 Agent 完成。

模拟器结果不能证明物理设备行为。一台设备的结果不能证明另一 OEM、Android 版本、profile 类型或分身环境的兼容性。

### debug 与 release 安装切换

配置前置条件以[本地签名基线](development.zh-CN.md#本地签名)为准。
以下是验证方法，不代表构建或安装已经通过：

1. 通过已授权构建取得两个 APK。使用 Android SDK 工具检查 APK 元数据与签名证书，
   例如 APK Analyzer 和 `apksigner verify --print-certs`。
   确认两个 APK 与已安装应用具有相同的 `applicationId` 和签名证书，
   并记录证书指纹、版本码和可调试属性。
2. 每次覆盖安装前检查版本码：正常覆盖要求待安装 APK 的 `versionCode`
   大于或等于已安装应用。标识与证书相同不能绕过 Android 降级限制；
   不得为了完成本检查而强制降级或修改项目版本。
3. 如果已安装应用使用旧的默认 debug 证书，则无法直接用这些 APK 覆盖安装。
   先通过可用且已验证的方法备份所需数据和设置，再由作者控制卸载并重新安装。
   不得自动卸载；如果无法备份，停止并询问作者如何保留数据。
4. 从兼容的 debug 安装开始，记录有代表性的已保存设置，
   随后覆盖安装 release，不卸载、不清除应用数据。重新打开应用，确认设置保留，
   并检查已安装包，确认其不可调试。
5. 按相同安装前置条件反向验证 release -> debug，
   确认已保存设置保留，且已安装包可调试。
   如果版本码阻止任一方向的验证，将该方向记录为未运行并说明原因。

使用上文证据字段与下文结果状态，分别记录两个方向的结果。

## 验证比例

- 纯文档变更：检查相关 Git diff，运行 `git diff --check`，并验证受影响的本地 Markdown 链接。除非另有要求，不运行 Gradle。
- 聚焦实现变更：在当前授权和环境允许范围内，使用最小的相关构建、自动检查和人工路径。
- 迭代完成：满足该迭代的验收证据，并按照迭代格式记录所有跳过、不可用、失败或未知的检查。
- 版本完成：只适用版本交付级别和契约选定的门禁。不得通过暗示把建议的更高级别证据变成强制要求。
- 设备与兼容性门禁：适用版本契约负责标识每个强制环境。未执行的建议 API、设备、OEM 或 profile 证据必须记录为 `Unknown`、`Not run` 或 `Unavailable`，不会仅因被列出就成为完成阻塞。建议检查一旦执行并发现纳入路径失败，就必须记录并解决，或返回作者明确处置；不得因该检查属于建议而忽略结果。
- 正式发布制品：适用[发布治理](release.zh-CN.md)和对应版本契约明确规定的额外矩阵、自动化、审查、签名、追踪与保留门禁。

## 结果报告

每项相关检查使用以下一种结果：

- `Passed`：所述命令或场景已运行，且验收条件成功。
- `Failed`：已运行并产生失败结果。
- `Not run`：有意未执行。
- `Unavailable`：由于所需工具、环境、设备、凭据或依赖不可用而无法运行。
- `Unknown`：证据不足，无法判断结果。

记录命令或场景、执行者、环境、适用时的日期和简要证据。不得根据代码检查、另一台设备、未注明来源的作者报告或没有观察到失败而推断通过。存在更新版本的提示属于维护信息，不是失败。

## 维护本基线

当 Gradle task 名称、已配置质量工具、设备要求、执行权限、证据字段或版本级验证职责变化时更新本文。功能特定验收条件保留在产品和迭代文档中；实际历史结果保留在适用迭代或版本记录中，不在本文持续累积。
