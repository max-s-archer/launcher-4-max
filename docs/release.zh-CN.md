# 版本、产物与发布治理

> 英文语义源：[release.md](release.md)。
>
> 本文是应用版本、已完成版本记录、APK 产物、签名连续性、Git tag 与 GitHub Release 的权威运营契约。本文不授权任何具体版本、tag、GitHub Release、公开分发或实现范围。

## 项目版本模型

Launcher4Max 使用项目自定义的 `MAJOR.MINOR.PATCH` 数字版本格式。该格式借用 Semantic Versioning 的三段结构，但以本文而非 Semantic Versioning 官方规范作为约束来源。

- 首个正式应用版本为 `1.0.0`，项目不使用 `0.x.y` 版本。
- 项目不存在预发布版本概念。`alpha`、`beta`、`rc` 以及 SemVer 的预发布或构建元数据后缀均不属于版本格式。
- `1.0.0` 以前的仓库 commit、已 push 源码状态、本地构建及其他工作属于开发证据，不属于正式应用版本。
- 正式版本标识一份可安装且已验证的 Android APK，不因纯文档工作而产生。
- 每个正式版本包含一个或多个已完成迭代。适用的版本交付契约从当前产品契约中选择该版本实际交付的子集。
- `1.0.0` 是首个最小可用版本，不要求实现当前产品契约描述的全部行为；其准确交付范围必须通过版本与迭代契约确定。
- 当前产品契约可以在版本规划、交付或完成期间继续变化。已完成版本记录保留其自身交付边界上被接受的范围和证据，因此可能与后来维护的当前产品契约不同，但不因此被追溯判定为错误。

## 交付级别

每份版本交付契约必须且只能选择以下一个交付级别。各级别逐步增加证据和运营义务；它们不是三套独立版本号体系，也不表示公开分发。

### 开发构建（Development build）

开发构建用于版本边界获接受前的实现、调查或聚焦验证。它可以是本地、临时、验证不完整并使用开发签名身份的构建，只需记录活动任务或迭代所需证据。开发构建不是已完成应用版本、作者日常使用基线、正式发布制品、里程碑或 Release。

### 作者日常使用基线（Author daily-use baseline）

作者日常使用基线是供项目作者持续使用的可安装版本。完成要求：

- 所选产品路径已经实现并得到接受；
- 记录已安装 APK 所对应的准确应用标识和源码 commit；
- APK 能够安装，并在至少一台作者指定的主要物理设备上成功完成所选核心路径；
- 不存在会使已验证日常使用不安全或不可用的已知纳入路径失败；
- 记录已知验证缺口、限制、恢复影响和后续归属；
- 实现和交付文档已经 commit 并同步到作者指定的共享 Git 历史。

除非适用版本契约明确将某项提升为门禁，否则建议自动检查、完整兼容性矩阵、性能分布、正式发布签名及备份、发布级制品摘要与归档证据、专业许可证结论、tag、发布和分发均不阻塞本级别。缺失证据保持未知，不视为通过。应保留足够的源码与 APK 身份信息，以便重新安装已接受基线；这不承诺 Android 数据回滚或降级支持。

### 正式发布制品（Formal release artifact）

正式发布制品是证据要求最高的交付级别。除作者日常使用基线要求外，其版本契约还要定义并满足必需兼容性环境、自动和手动验证、性能或可靠性阈值、依赖和许可证处置、merged manifest 与安全/隐私审查、稳定发布签名保管和恢复、制品摘要、外部保留，以及从源码到制品的完整追踪。即使本级别已经完成，tag、GitHub Release、商店操作、上传和公开分发仍须另行授权。

作者可以通过后续单独授权的交付契约或版本，将已完成的较低级别版本提升到更高级别。不得追溯声称原完成边界当时并不存在的证据。

## 数字递进规则

每次发生变化的数字位只能严格加一。除非项目作者明确替换本契约，否则禁止跳号。

- `PATCH` 用于当前产品与版本契约内的兼容性实现修正，每次只加一；`PATCH` 增加时，`MAJOR` 与 `MINOR` 不变。
- `MINOR` 用于当前能力层级内的用户可见能力、主动行为变化或显著可用体验提升，每次只加一；`MINOR` 增加时，`PATCH` 归零。
- `MAJOR` 仅在进入下一个已授权能力层级时加一；`MAJOR` 增加时，`MINOR` 与 `PATCH` 归零。
- 前一位数字增加时，其后的所有数字位始终归零。

`MAJOR` 数字专门对应产品能力层级：

| 版本族 | 能力层级 |
| --- | --- |
| `1.x.x` | V1：固定呈现 |
| `2.x.x` | V2：基础适应 |
| `3.x.x` | V3：AI 能力 |
| `4.x.x` | V4：Agent 能力 |

在进入 V2 的契约得到明确授权前，所有正式版本均保持在 `1.x.x`。重大项目进展或不兼容变更本身不允许增加 `MAJOR`。同一能力层级内的不兼容变更使用下一个 `MINOR` 版本，并必须记录其影响与迁移要求。

纯文档变更永远不改变应用版本。影响 APK 的源码、资源、Manifest、依赖或构建配置变更可以成为新正式版本的理由，但普通代码变更只有在作者宣告版本边界且所需证据齐备后才成为正式版本。

## Android 版本标识

- Android `versionName` 使用本文定义的正式 `MAJOR.MINOR.PATCH` 值。
- Android `versionCode` 在 `1.0.0` 时从 `1` 开始。
- 每个因安装分发、交付验证或上传可观测性平台而成为可追踪制品的 APK，都必须使用下一个尚未使用的 `versionCode`，并且严格加一。
- 未保留、未分发、未作为交付证据且未上传可观测性平台的重复本地构建，可以复用其配置的 `versionCode`。
- 已完成正式版本使用其制品获接受边界时下一个尚未使用的 `versionCode`。在该边界之前，计划中的 `versionCode` 只是暂定值。
- `versionCode` 不根据 `versionName` 计算；分配序列不得跳号，已分配值不得回收、不得用于另一个不同的可追踪 APK，也不得降低。
- 两个不同的正式 `versionName` 不得共用同一个 `versionCode`。
- 产品更名为 Launcher4Max 时，`applicationId` 由 `com.avenor.launcher` 变更为 `com.maxarchm.launcher`。Android 因此把更名后的应用视为全新安装：既有的 Avenor 安装不会原地升级，其本地收藏与 Drawer 显示设置对更名后的应用不可见。受支持的迁移路径是：先在旧应用的 Settings Data 导出中备份收藏与显示设置，安装 Launcher4Max 构建，恢复该备份文件，重新选择默认桌面角色并重新启用无障碍服务，最后再移除旧应用。恢复路径接受旧的 `avenor-backup-` 文件名，因为恢复按备份内容而非文件名解析。
- 不支持降级。

## 应用标识迁移

当前 `applicationId` 为 `com.maxarcher.launcher`，替代 `com.maxarchm.launcher`。
即使签名证书和版本相同，Android 也会将其作为独立应用安装。
它无法原地升级旧包，也不会自动访问旧包的私有数据。
上文记录的 Avenor 更名仍为历史迁移事实。

1. 移除旧应用前，先通过旧应用的 Settings Data 导出备份。
2. 安装新应用标识的构建，并手工恢复导出的备份。
3. 重新选择新应用作为默认 Home；若使用无障碍锁屏，重新启用新应用的无障碍服务。
4. 检查恢复后的设置与收藏，再移除旧应用。

本次标识变更不修改备份 schema，也不增加自动数据迁移。
备份中的组件标识不会从旧 Launcher 包自动重写为新包。
旧 Launcher 自引用仍沿用既有恢复与可用性处理；恢复后应检查这些条目。
Android 角色与服务授权不会通过备份恢复。
发布验收前仍需完成构建、安装和设备迁移验证。
本次源码变更不宣告正式版本完成，也不分配新的制品版本。

## 构建身份与可观测性

产品版本、APK 构建序号、构建阶段、源码修订和 Git 里程碑身份是相互独立的维度：

- `versionName` 表示产品版本并遵循项目版本模型，不编码开发阶段、监控状态或 tag 状态。
- `versionCode` 用于区分有顺序的可追踪 APK 构建。开发制品与发布制品不通过奇偶分配、正式版固定 `+2` 或其他预留数字模式进行区分。
- 可追踪的开发或内部 APK 可以使用计划中的目标 `versionName`，但这不会宣告该产品版本已经完成，也不会添加后缀或产生预发布版本。
- 每个可追踪 APK 记录都要以 `development`、`internal` 或 `release` 标识其构建阶段，并记录准确的源码 Git commit。这些阶段标签属于制品元数据，不引入预发布版本格式。
- 每个已分配的 `versionCode` 及其 APK 身份都要记录在适用的迭代或交付证据中；即使该构建随后被拒绝或取代也不得删除，以保证下次分配明确无歧义。
- 未来采用可观测性或崩溃监控平台时，上传的构建身份必须可追踪到 `applicationId`、`versionName`、`versionCode`、构建阶段和源码 commit。平台专有的发布标记不得替代项目交付记录。
- 构建不会仅因上传到监控平台或在其中标记为 release，就成为已完成正式版本。
- 授权监控集成前，必须审核隐私、安全、数据收集、同意或披露、依赖与许可证影响、符号或 mapping 文件保管、访问控制、保留规则和上传权限。

在同一 `MAJOR` 版本族且应用标识相同的情况下，任意较旧正式版本必须可以直接升级到任意较新正式版本。
上述应用标识迁移无论配置版本号为何，都需要独立安装并手工恢复。
跨 MAJOR 升级必须由适用的大版本交付契约在发布前定义支持的来源版本、迁移方式、验证和限制。

## 迭代与已完成版本记录

每个版本从规划到完成始终使用一个稳定的 `docs/delivery/<version>/` 目录。其中的 `delivery.md` 记录所选交付级别、完成条件和事实结果。版本完成不会重命名或移动目录，而是使版本及其已完成迭代记录成为受保护的交付历史。下列事项在适用时记录：

- `versionName` 与 `versionCode`
- APK 对应的准确 Git commit
- 纳入的迭代及宣告版本边界的理由
- 重要产品变化与实现变化
- 迁移或兼容性影响
- 已完成的验证证据及涉及的设备或环境
- 已知限制、未解决缺陷和其他遗留问题
- 可用 APK 或构建身份
- 所选级别要求时记录 APK SHA-256 摘要
- 所选级别包含稳定签名身份时记录签名证书 SHA-256 指纹
- 存在时的相关 Git tag 与 GitHub Release

已完成版本记录不得包含私有签名密钥、keystore 密码、密钥密码或其他签名秘密。

## APK 产物契约

需要保留已完成版本 APK 时，将其存储在本产品仓库之外。
具体目录由项目作者保管，并且可以变更；本仓库不记录该目录。
作者于 2026-09-23 接受所选目录可以同时存放其他私人文件。
除非版本契约另有要求，作者日常使用基线可以不保留 APK；正式发布制品必须保留。

- APK 文件不得提交到 `launcher-4-max` Git 仓库。
- 本文不决定其他仓库是否跟踪这些 APK。在获得明确决定前，该位置只表示外部文件系统存储，不构成提交二进制产物的授权。
- 本文不定义同步或备份周期。
- 为保持外部归档命名一致，使用
  `<product>-v<versionName>-vc<versionCode>-<stage>-<shortCommit>.apk` 格式，
  例如 `launcher4max-v1.7.0-vc8-release-8523e0f.apk`。
- 文件名仅用于身份识别和归档辅助，不替代 APK 的 `applicationId`、
  `versionName`、`versionCode`、完整源码 commit、SHA-256 摘要或适用的签名证据。
- 记录的 SHA-256 必须由准确的归档 APK 计算，并在复制到外部位置后再次验证。
- 当相关证据可用时，产物记录还必须标识生成并验证 APK 的构建时间与环境。

APK 只有在可安装、通过所选交付级别要求的验证，并匹配已记录的源码 commit 与版本标识后，才代表已完成版本。只有所选级别或版本契约要求时，才必须具备摘要和签名指纹证据。

## 签名连续性与保管

每个正式发布制品必须使用同一稳定发布签名身份，使受支持的更新可被 Android 识别为同一应用的更新。作者日常使用基线可以使用现有开发签名或作者控制的签名身份，但版本契约必须记录由此产生的安装和更新限制。

- 发布 keystore 由项目作者创建或明确授权创建，并由项目作者保留所有权和最终控制权。
- 发布 keystore、私钥、密码和签名属性文件必须位于 Git 与权威项目文档之外。
- 发布 keystore、密码及其备份由项目作者保管在 Git 与权威项目文档之外。作者于 2026-09-23 决定自行完成保管与备份，不在本仓库记录位置、格式、参数或流程。
- 首个正式制品之前的两份独立加密备份要求仍然有效；满足该要求是作者动作，不是本文记录的流程。
- 每份适用的已完成版本记录只保存发布证书的 SHA-256 指纹，永不记录私有签名材料。
- 在首个正式发布制品之前，项目必须为发布 keystore 和必要恢复信息建立安全存储，以及至少两份相互独立、加密且由作者控制的备份。
- 签名身份丢失、泄露、轮换或迁移到平台托管方案时，必须在宣告下一正式版本前获得作者明确批准、完成影响评估并记录迁移决定。

未来若决定通过 Google Play 或其他商店分发，必须另行定义平台托管签名、上传密钥、渠道要求及迁移影响。目前未授权任何分发平台。

## Git tag 与 GitHub Release

应用版本、Git tag 与 GitHub Release 是相互独立的记录：

- 每个正式版本都保留已完成交付记录，但并非每个正式版本都创建 Git tag。
- 当积累的相关功能或体验提升形成重要且稳定的实现基线时，适合创建 tag。例如，`1.0.0` 可以不创建 tag，而后续 `1.3.0` 可以成为带 tag 的基线。
- 创建 tag 及其准确目标 commit 必须得到项目作者明确批准。Agent 可以建议某个版本是否值得创建 tag。
- 创建 tag 时，名称采用 `v<MAJOR>.<MINOR>.<PATCH>`，与已接受的 `versionName` 一致，例如 `v1.7.0`。不使用预发布后缀。
- tag 必须是 annotated tag，说明为 `release: <tag>`；每个已发布版本只对应一个 tag，不得强制移动或删除后重建。
- 它指向已接受 APK 所代表的准确源码 commit，在 `main` 上创建，且不改变 `versionName` 或 `versionCode`。
- 创建 tag 与使用 `git push origin <tag>` 推送各自单独授权。
- 若不存在先前的 release tag，Release Notes 的比较范围由作者指定，不默认取整段历史。
- 创建 tag 不增加或以其他方式改变已接受 APK 的 `versionName` 或 `versionCode`。tag 必须指向该制品所对应的准确源码 commit。
- 创建 tag 不要求同时创建 GitHub Release。
- GitHub Release 必须引用一个已存在且获批的 tag，并需要项目作者另行明确批准。
- 版本完成不要求创建 GitHub Release。当前发行渠道仅为公开 GitHub 仓库。
- 把经过验证的 APK 附到 GitHub Release，或使用任何其他渠道，都需要作者另行批准及其适用的安全与验证门槛。
- 本文与已完成版本记录均不授权创建 tag、远程 push、GitHub Release 或上传 APK。

在本项目中，只有项目作者明确宣告某个重要基线，并且其获批 Git tag 已存在时，里程碑才成立。GitHub Release 可选；作者选择对外发布时，仍须另行批准。版本或虽已获批但未被宣告为里程碑的 tag，不会自动构成里程碑。

## 迁移成本约束

产品定义、技术调研、架构与实现必须考虑未来能力层级可能产生的迁移成本。在证据支持时，应保留可替换边界、数据迁移路径以及适当的扩展点或 API 接缝，避免后续能力层级产生不必要的重写。此要求不授权投机性框架、未使用抽象或在产品文档中规定实现细节；所有准备必须与当前证据相称，且不得静默扩大当前范围。

## 尚待实现阶段决定的事项

已于 2026-09-23 决定：

- 保留的 APK 放在本产品仓库之外、由项目作者保管的目录。是否由其他仓库跟踪，以及同步或备份周期，仍未决定。
- 发布 keystore 的保管与备份由项目作者自行处理，不在本文记录。
- 创建 tag 时采用 `v<MAJOR>.<MINOR>.<PATCH>` 的 annotated tag。见 Git tag 与 GitHub Release。
- 本发行阶段不使用可观测性或崩溃监控平台。
- 发行渠道仅为公开 GitHub 仓库。GitHub Release、tag 或 APK 上传仍须单独授权。
- 权威命令：用 `./gradlew assembleRelease` 构建并签名，输出 `app/build/outputs/apk/release/app-release.apk`，签名配置取自本机 `keystore.properties`；用 `aapt2 dump badging <apk>` 核验产物身份；用 `apksigner verify --print-certs <apk>` 核验签名证书；用 `shasum -a 256 <apk>` 计算摘要，并在复制到保留位置后重算比对；用 `./gradlew lintRelease`、`./gradlew testDebugUnitTest` 与 `./gradlew connectedDebugAndroidTest` 验证。设备安装与升级在设备上直接打开 APK 完成，因此不记录主机侧安装命令。
